# P4: the profile

P4 makes what a tool that reads RO-Crates, and cannot run QRO-Crate's checker, needs of the profile: a Profile Crate that
describes it, a description the profile's IRI resolves to, the vocabulary's context, SHACL shapes in Turtle, and examples.
Everything is generated from the vocabulary table, so a row and its shape cannot disagree.

**The checker is the authority.** A shape is a consequence of what the checker holds, never an authority beside it. Each shape
says in `qs:claims` which refusals it mirrors, then the six refusals of steps 1 and 2 that can come before its own and that RDF
cannot show: `spelling`, `term-unknown`, `graph-form`, `context`, `file-missing` and `file-link` (`FORM` in `qro/p4_shapes.py`;
what each is for is in "How the table becomes shapes"). Tests hold two things, and the second is narrower. When a must shape
fails, the checker refuses the crate. When the crate is one fault away from one the checker accepts, it refuses it by a name a
failing shape claims: over the plants, the first verifier's pool of single edits, the second verifier's three families of crates
and the alias-key crates, which are samples. A crate with several faults is refused too, but by a name that no failing shape
need claim. A crate the expansion cannot read, one with an id the reader refuses or a context of its own, is never left out: the
evaluator abstains from it and the checker has refused it, and the engine stage reads the contexts through a real engine. They do
not prove it, and limit 19 says what is held of ids and at which base: [the limits](#the-stated-limits) say what the shapes
cannot see.

## What is in profile/

| path | what it is | made by |
|---|---|---|
| `ro-crate-metadata.json` | the Profile Crate (RO-Crate 1.3): root, resources, files with digests, the vocabulary as DefinedTerms | `tools/gen_profile.py` |
| `README.md` | the description the profile's IRI resolves to: the declaration, the levels, the limits, every shape with an anchor | `tools/gen_profile.py` |
| `EXAMPLES.md` | the matrix: what the checker and the shapes each say of every example and plant | `tools/gen_profile.py` |
| `context.jsonld` | the context a QRO crate inlines | P0's `tools/gen_vocabulary.py`; P4 reads its bytes |
| `validator/qro-crate/profile.ttl` | the rocrate-validator profile description | `tools/gen_profile.py` |
| `validator/qro-crate/must/*.ttl`, `should/*.ttl` | the shapes, a folder a requirement level; a folder with no shape is not written | `tools/gen_profile.py` |
| `examples/fixture/` | a copy of P0's fixture crate | `tools/gen_profile.py` |

No Python sits under `profile/`: the lint names every top-level directory that holds Python. Every generated file is ASCII
with LF line ends, and two renders are the same bytes whatever the host: nothing is read from a clock, a path, a user or a host.

## Regenerating

```
python tools/gen_vocabulary.py --write    # P0's: the context, the vocabulary, the refusals, the controls
python tools/gen_profile.py --write       # P4's: everything else under profile/
python tools/gen_profile.py --check       # the profile stage, in the quick budget
```

Run them in that order after any change to `qro/vocabulary.py`: the Profile Crate lists the digest of `context.jsonld`, so each
tool fails its own `--check` until it is run. `--check` compares bytes, lists a file that no definition renders, a link and a
directory that holds no file, and holds the Profile Crate to the rules of RO-Crate 1.3's profiles page that its bytes show: those that
`check_profile_crate` lists in its docstring, which the limits (9, 11, 17 and 22) complete with the SHOULDs it does not meet. The
check reads any Profile Crate, however misshapen, and refuses what it cannot read by a problem it names; it is never why the tool
answers 3. `--write` renders every file, and holds the result to the same check, before it writes any; it removes a file under
`profile/` that no definition renders, a link, and a directory that holds no file, P0's context aside.

**Links.** A link is a symbolic link or a directory junction, by the checker's own test (`checker._is_link`, FORMAT.md item 12),
which every walk of the tool asks of every entry and no walk of its own makes: `os.walk(followlinks=False)` leaves a symbolic
link alone but descends a junction, which `Path.is_symlink` does not call a link (MEASURED on Windows, Python 3.12). A link is
never descended, never read through, never written through and never removed through, and that holds for `profile/` itself.
**A link at `profile/` is refused, in both modes, by a named problem and exit 1, before anything under it is read, listed,
written or removed.** The fourth verifier's D1 (MEASURED): with a junction at `profile/` to a directory outside the tree that held
a copy of the rendered files, a file and an empty directory, `--check` read the copy through the link and named the file as a
stray, and `--write` removed the file and the empty directory and wrote the rendered files there; with the junction pointing at the
tree's own root it removed two files of the tree, then the link, and failed; with it pointing at an exact copy `--check` said the
tree was clean. The walk had asked of every entry under `profile/` whether it was a link, and never of `profile/`. The question
about `profile/` is now the first thing either mode asks, so it comes before the definitions are even checked. Below `profile/`,
`--check` lists a link by its path (for a junction at `profile/validator`, `profile/validator is a link, which no definition
renders`), and **`--write` removes the link itself and goes on, where it might have refused to write.** Why: it is what the tool
has always done with a symbolic link; `profile/` is a crate, and a crate holds files and never a way out of itself, so a link
under it is something no definition renders, as a stray file is; a refusal would leave the tree stale until someone removed the
link by hand, with nothing gained, since in neither choice is anything behind a link read, written or removed; and a link where the
tool has files to write (a junction in the place of `validator/`) must go before them, or they would be written behind it. P0's
`context.jsonld` is never read through a link and never removed: a link or a directory there is refused by a sentence that says
which it is (before, a junction there was called missing, "not there"; a junction whose target is gone is none that the checker's
test finds on the owner's machine, and it is a context that is missing there, exit 1: the stated limits of the tool, below). Held
with real junctions, made without privilege (`_winapi.CreateJunction`, as the plant of `file-link` is), whose targets are there
when the test ends, and which a fixture's teardown removes at the end of every test, passed or failed, while their targets are there
(`remove_links_under` in `tests/p4/p4_helpers.py`, so that a failing run strands none): in `tests/p4/test_p4_tree.py`, `profile/`
itself to a directory outside the tree that holds a copy of the rendered files, a file and an empty directory, to an exact copy and
to the tree's own root, each mode, in process and as a process, with a spy that finds nothing under the link listed, walked or
opened, and what is behind it equal byte for byte before and after; and in `tests/p4/test_p4_tool.py` a link below `profile/`, in
process and as a process. A link that leads nowhere, a junction whose target is gone, is not made: the owner's machine cannot open
one (the stated limits of the tool, below), so the tests of it tell the tool that a link stands at the path, with a stand-in shown
to lead nowhere to every call that could ask (`os.stat`, `os.lstat`, `os.path.exists`, `isdir` and `isfile`, `os.path.realpath`
with `strict`, a listing) and a control that each telling took, and hold what the tool then prints, exits, writes and removes
(`tests/p4/test_p4_tree.py`).

**What `--write` does with the rest of a tree**, so that `--check` never advises what `--write` cannot do (the fourth verifier's
other findings, each MEASURED on this host and reproduced before the fix):
- It writes each file beside its place and puts it there with `os.replace`, never through the place itself, so that a hard link at
  a rendered path keeps the bytes of its other name (before, it wrote through: on this host the sandbox's guard refused, and
  elsewhere the file outside the tree would have been overwritten). It always puts a new file there, so a hard link that held the
  right bytes is clean to `--check` and is broken by `--write`. A temporary file it made and could not put in place is removed
  again, and a file it did not make never is.
- A name that differs only by case from a rendered path or from P0's `context.jsonld` (`Validator/` or `Context.jsonld` on a host
  that ignores case, `readme.md` on any) is never removed or renamed: both modes refuse it by a named problem, exit 1, and
  `--write` removes and writes nothing while one is there (before, it removed P0's file as a stray, and on a host that ignores case
  left `--check` failing after `--write`). A directory spelt another way that holds only strays is no clash: its strays go, it goes
  with them, and the right one is made.
- It removes the strays, then every directory that holds no file, and only then writes, so that a directory where a rendered file
  goes is cleared, with what it held (before, `--check` advised a `--write` that failed with exit 3 every time, since the empty
  directories were removed after the writes), and `--check` says "a directory, not the file its definition renders".
- A directory the host will not list is raised, as the checker's walk raises it, and not passed over (before, both modes exited 0
  and never named it): the tool fails, exit 3, and names it. Tested by simulation, `os.scandir` made to raise `PermissionError`
  for one directory, in process and as a process, as the verifier did: the sandbox's guard refuses the extended paths a real one
  needs.
- A crash is never exit 1, which is the drift verdict's code and Python's for an uncaught exception (before, `python -OO` died
  with a traceback and exit 1: it strips the docstring the argument parser took its description from). A failure in the arguments,
  in the work, in a module the tool imports that will not import, an exit or an interrupt raised among them, and a failure to say a
  failure, is exit 3 and, where there is somewhere to say it, one escaped line; argparse's own exits, 2 and `--help`'s 0, stay.
  Where a stream is closed (`None`) a mute one stands in for it, so that a line that cannot be said is no crash and the exit code
  still carries the verdict. Held by `tests/p4/test_p4_crash.py` and `tests/p4/test_p4_tree.py`. `tools/gen_vocabulary.py`'s own
  `-OO` fault is P0's, and is not touched here.

**Stated limits of the tool.** A file with the read-only attribute is neither removed nor replaced on Windows (MEASURED,
`PermissionError`): `--write` fails on it, exit 3, naming the files it had finished writing, and `--check` is not affected; where
the directory, not the file, decides, it is replaced. An entry that is no regular file, directory or link (a pipe or a device, on a
host that has them) is read as a file would be. The two spellings of a name are compared by Python's `casefold`, not by the host's
own table, so a name the host calls the same and `casefold` does not is no clash (it is a stray, and removed). A hard link is
not a link to `checker._is_link`, and `--check` does not report one. A junction whose target is gone is a link only on a host that
can open it, and the owner's machine cannot (found so on 2026-10-30, Windows 11, Python 3.12, and again on 2026-10-31: `os.lstat`
of it raises `FileNotFoundError`, or `NotADirectoryError` where its target has become a file, so the checker's test of a link finds
none there, and removing the junction, tried by `os.rmdir`, `os.unlink`, `shutil.rmtree`, `cmd`'s `rmdir` and a rename, fails until
its target is made again; the cause is not known). With `profile/` itself one, or with one at P0's `context.jsonld`, both modes
refuse the tree, exit 1, as one whose context is missing (`profile/context.jsonld is missing: run tools/gen_vocabulary.py
--write`), for it is read and not listed; with any other below `profile/`, both fail, exit 3, naming a directory the host cannot
list (`Unlistable`, with `FileNotFoundError`, or `NotADirectoryError` where the target has become a file); neither writes or removes
anything. The tool's code does not change for it: a host that opens such a junction answers the checker's test with a link, and the
walks, the refusal and the removal are those of any link, which is what the tests hold by telling the tool so. Where its stdout's
reader is gone, Python itself ends the tool with exit 120, as `tools/gen_vocabulary.py` does.

A name the output's code page cannot write, a stray file's, is written as its escape on every line of both modes, never a crash:
before, `--write` exited 3 after it had removed the file and before it wrote anything (P4's third verifier, note 4, MEASURED with a
name in CJK characters and stdout in cp1252). The streams are told so as P0.6's gate tells its stdout, and left as they are where
they cannot be told (a stream with no `reconfigure`).

Exit 0: clean. 1: drift, a file missing or unexpected, a link, a name that differs only by case, a directory that holds no file or
stands where a file goes, a Profile Crate that fails its check, or a `profile/` that is a link. 2: the definitions contradict
themselves (`V.sanity()`, which holds the naming rule, a spelling with no shape constraint, a pattern outside the syntax an
engine shares, a shape the model calls incoherent), or the arguments are wrong. 3: the generator itself failed, in one escaped
line on stderr; never a verdict.

`datePublished` is one constant (`DATE_PUBLISHED` in `qro/p4_profile.py`), the build's day, never the clock. The lead sets it at the
release, with the tag.

## How the table becomes shapes

| family | from | level | claims of its own |
|---|---|---|---|
| `term-*`, one a row | the row's spelling, absence words and cardinality; a regular expression is read from `qro/spelling.py`, never written again | must | `spelling` |
| `domain-*`, one a row whose domain is not `*` | the row's domain | must | `graph-form` |
| `entity` | every term and every type of the table, closed | must | `term-unknown`, `field-kind`, `graph-form` |
| `descriptor` | `V.descriptor()` | must | `graph-form` |
| `root` | `V.ROOT_REQUIRED`, the two profiles, the action types | must | `graph-form` |
| `action-mentioned` | the action types | must | `graph-form` |
| `file-digest-present`, `rawresult-form` | `PRESENCE` in `qro/p4_shapes.py` | must | `file-digest`, `raw-digest`; `raw-form`, `graph-form`, `file-unlisted` |
| `file-reached` | the descriptor's `about`, and `hasPart` | must | `file-unlisted`, `graph-form` (a reference that names nothing) |
| `profile-entities`, `profile-version` | `V.profile_entities()` | must | `graph-form`; `context`, `graph-form` |
| `absence-*` | a term with absence words on a typed domain: rule 2 | should | none: the checker accepts |

**FORM.** The claims published are those, then the six names of `FORM` that a must shape does not name already (`groups` adds
them): the refusals of steps 1 and 2 that RDF cannot show, or shows as another graph, so that any must shape can fail on a crate
the checker refuses by one of them.

| name | RDF does not show | found by |
|---|---|---|
| `spelling` | an empty list, a list of one, a bare value where a list stands: another graph | the first verifier, defect 2: 202 of 12,591 single edits |
| `term-unknown` | a key or a type spelt another way: the same predicate or class | the same: 65 of 124 crates with an alias key |
| `graph-form` | an @id twice (RDF merges the nodes, so a single-valued term has two values); two paths that differ by case, or a path that is a file and a directory (RDF holds two nodes, and the one added, a File with no digest, fails a shape); a reference that names no entity (`_:b0` is a blank node to a real engine); a top-level `@reverse` | the second verifier, defect 1(a), and the lead's ruling of 2026-10-19T17:41:46Z for the references |
| `context` | a top-level `@context` of the crate's own: a real engine reads it, so a term it redefines is another predicate | the second verifier, defect 1(b) |
| `file-missing` | a File entity with no file under its name (an added entity has none on disk): step 2 refuses it before the digest and the listing, whichever shape the entity fails | the second verifier, defect 1(c) |
| `file-link` | a link in the crate: the walk refuses it before anything else of step 2 | the lead's ruling of 2026-10-26T11:18:27Z, from reading `checker.walk` |

The other refusals of steps 1 and 2 are claimed by the shapes that mirror them (their own claims, above): `field-kind` by
`entity`, `file-unlisted` by `file-reached` and `rawresult-form`, `file-digest` and `raw-digest` by `file-digest-present`. A test
holds that, against the vocabulary's refusals: one P0 adds to steps 1 or 2 is a decision here, and not a silence
(`tests/p4/test_p4_shapes.py`). Step 3 is pinned the same way (`tests/p4/test_p4_sweeps.py`, the third verifier's note 5):
it refuses `graph-form` (`FORM`'s), `raw-form` (`rawresult-form`'s) and `count-unpaid`, which no shape claims, because RDF holds
`qro:shots` as the number it is and cannot compare it with the bytes: the one-edit crate that reaches it, a stated count the file
does not hold, conforms to every must shape, so nothing is left unclaimed, and the pool's `qro:shots` edits hold it.

**Measured.** Before the ruling, with the two names of round 1, the second verifier's crates made a must shape fail under a name
no failing shape claimed: of the 378 duplicate-id additions to the fixture 12, in 9 classes, of 320 added Files 28, in 3, and 6 of
the 8 variants of the context (the evaluator abstains from these, so the report counts what pyshacl fails). The three families as P4 makes them
are 469 crates, and with the two names of round 1 the sweeps find 49 of them under a name no failing shape claims, in 20 classes
(`file-link` among them); with the six, none (MEASURED, `tests/p4/test_p4_families.py`). Each name is seen needed: with it taken out
of `FORM`, the sweeps find a crate unclaimed, and `context`, which the evaluator cannot see, is found by the engine stage.
`file-link` is claimed from reading `checker.walk`, and it is also planted: a File added at the path of a link is refused
`file-link` with `file-digest-present` or `file-reached` failing. A symbolic link needs a privilege on Windows that this host
lacks (MEASURED, WinError 1314), but a directory junction needs none (`_winapi.CreateJunction`, the way `tests/format/test_hostile.py` makes one); on a host
with symbolic links the test makes those. The test does not skip, since a test that skips fails its stage.

**The `ref` rows.** The ruling of 2026-10-19T17:41:46Z gave the 18 rows whose spelling is `ref` (`about`, `conformsTo`,
`mentions`, `license`, `hasPart`, `instrument`, `object`, `result`, `qro:device`, `qro:line`, `qro:record`, `qro:knownAnswer`,
`qro:calibration`, `qro:historyAtRunning`, `qro:law`, `qro:lawCircuit`, `qro:measuredPub`, `qro:heldCompile`: 18 on 2026-10-26)
`graph-form` beside their own `spelling`, after the plant `abstains-blank-node-reference`: FORMAT.md item 22 has the checker
refuse a reference outside the id rule `graph-form` where it is no absolute IRI (`_:b0`, `./x`: it names no entity) and
`spelling` where it reads as one (`schema:a`), and a real engine reads `_:b0` as a blank node, which the node kind of a `ref` term's
shape refuses. The second verifier found the same gap on every other term, and `FORM` now holds `graph-form` for every must shape,
so the ruling is superseded; what it found stays as evidence. A real engine fails each `ref` term's shape on `_:b0` and on no
other reference, on all 18 terms (MEASURED, 288 crates, pyshacl 0.40.1), and ten shapes that are no `ref` term's also fail on such
a reference: `descriptor`, `root`, `file-reached` and seven `domain-*` shapes (a reference put on `about` replaces the descriptor's
one value, so the root is no longer what the descriptor is about, and `root` also fails on a third `conformsTo` or on a `mentions`
that is no action). The evidence is held by `tests/p4/test_p4_refs.py` (the evaluator, over references of each kind on every such
term) and `tests/p4shacl/test_p4shacl_refs.py` (a real engine, over all of them, and the claim taken away from those shapes
watched failing).

A row gained by a later parcel gains its shapes with no edit of P4's. What the table does not say is where a term is *required*:
those rules are `PRESENCE`'s, P4's own, until the table has a `need` for them (P4's design, R-A, declined for now). A presence rule
a later step adds is then not a must shape until someone writes the line: weaker than the checker, never stricter.

## Examples and plants

`profile/EXAMPLES.md` is rendered from `qro/p4_examples.py`. A plant is one fault in P0's fixture crate, with what the checker
must say and which must shapes must fail. Four kinds of fault are written by hand (faults the shapes see; faults only the checker
sees; edge cases the checker accepts; ids the reader refuses and the expansion cannot read), and three families are made from the
table: a value in no spelling of a term, a term where its domain does not admit it, and a single-valued term given two values.

**What the checker says of a hand-edited fixture.** Step 9 refuses any edit of the fixture's metadata, as `metadata-generated`, so
that verdict also means that steps 1 to 8 accepted the crate. The edge cases rely on it: every must shape has to conform to a crate
that reaches step 9. Found by reading the checker, not by running the shapes: the first draft of the design had the root asking
what its `hasPart` names, and a File with an absolute id of another scheme asking for a digest, and the checker holds neither.

**The `abstains` family is the exception.** The reader refuses those crates' ids (FORMAT.md item 22) and the expansion refuses to
read them, so the checker has refused each, as `spelling` (`graph-form`, for the reference), and the evaluator says nothing. A
real engine reads them its own way: it fails `entity` on a blank-node id, `term-name` on an id that begins with an at sign (the root
to rdflib, which then has two names), `file-digest-present` on an absolute `file:` id and `term-haspart` on a reference to a blank
node. The matrix says so, and an engine-stage test holds it, and that the checker refused each first, by a name the failing shape
claims: `spelling` for an id, and `graph-form` for that reference, which `term-haspart` claims as every must shape does (limit 19).
The test finds no plant whose refusal no failing shape claims, and with `graph-form` taken away from the shapes of the 18 `ref`
terms it finds `abstains-blank-node-reference` again. A top-level `@context` of the crate's own is a crate of the same kind, which
the plants do not make (a plant edits the entities): the evaluator abstains from it, a real engine fails `entity`, `root` and
others on it, and the checker has refused it `context`, which every must shape claims. The engine stage reads eight of them.

Only P4's own plants are listed. Every other parcel's crate plant is held to the shapes' soundness, and never listed. A plant of
another parcel whose control row says `accepted` is judged by the gate with no edit of P4's.

## The stated limits

They are written once, in `qro/p4_profile.py` as `LIMITS`, and rendered into `profile/README.md`. These are the ones about the build and the way it is held:

- the shapes are held to one engine and to an evaluator of this repository's, and regular expressions are Python's `re` in both;
  **the shapes are for an engine run without inference**: pyshacl's `inference` is `none`, its default, and with `rdfs`, `owlrl`
  or `both` it fails the accepted fixture crate on `descriptor`, `entity` and `profile-entities`, with 94, 112 and 527 results

  (limit 2);

  boolean, differently, and the generated shapes use neither; and they read an integer's lexical form differently, on forms

## The permanent IRI

The IRIs are placeholders (Logan, 2026-10-16: he will register a permanent one once the project is more complete). A permanent IRI

## Facts learned in the build

- pyshacl reports a result with the severity of the shape that produced it, and a node shape's severity does not reach the property
  shapes inside it, so the writer puts the level on every property shape that reports.
- `sh:pattern` is a search with Python's `re`, and `$` matches before a final line feed: a pattern is looser than the checker's
  `fullmatch` by one trailing line feed, which a fixed length closes.
- `pyshacl.validate(..., meta_shacl=True)` with no shapes graph validates the data against itself; the meta check is
  `pyshacl.entrypoints.meta_validate`, and its verdicts are the same with rdfs inference, none and unset on the five shapes tried.
- RDF cannot tell a key spelt another way from the table's own (`schema:name` is `name`), an empty list from a missing term, or
  a list of one from a value; the reader refuses each by a name that comes before any value is read. So any must shape can fail
  on a crate refused `spelling` or `term-unknown`, and every must shape claims both (the verifier's round 1, defect 2). Four more
  come first, and RDF shows them not at all or as another graph: an @id added again is one node in RDF, so the same single-valued
  term has two values; a context of the crate's own is read by a real engine and abstained from by the evaluator; a File entity
  added with no file under its name is refused by step 2 before its digest and its listing; a link is refused by the walk before
  anything. So every must shape claims those four too (the second verifier's round 2, defect 1).
- A directory junction is a link to `checker._is_link` (`Path.is_junction`), and `_winapi.CreateJunction` makes one with no
  privilege, where `os.symlink` fails with WinError 1314 (MEASURED 2026-10-26). The report of the second verifier thought the host
  could make no link, and `file-link` was ruled claimed from reading; a test plants it. The same junction is no symbolic link to
  Python: `Path.is_symlink` and `os.path.islink` say false, `os.walk(followlinks=False)` descends it, and `unlink` and `rmdir` each
  remove the junction and leave what it points to (MEASURED 2026-10-26, Python 3.12). The generator's walks followed one until the
  third verifier's run (D1); each now asks the checker's test (see "Links" above).
- RO-Crate 1.3 (READ 2026-10-16 through WebFetch, the profiles page and the data entities page): an entity that represents a
  JSON-LD context MUST have an absolute `@id` and the encodingFormat `application/ld+json`; a file present in the crate root is
  not to be given a web-based identifier. So the Profile Crate holds `context.jsonld` as a File with a relative path, whose
  `sameAs` is the context's absolute IRI, and a contextual entity at that IRI.
- A fragment with a colon, `#a:b`, is no compact IRI: JSON-LD splits it at the colon, finds in `#a` neither a prefix of the
  context nor a scheme, and so resolves the id against the base, and rdflib makes `file:///crate/#a:b` of it (MEASURED at the
  resume, 2026-10-19). The first run of the ids test found the expansion refusing 616 of 14,052 accepted ids for this one reason.
  It now reads a fragment before it looks for a prefix. The first build abstained from such an id, as from a blank node,
  having no reading for a colon after a #; rdflib resolves it like any other fragment.
- Four of the 57 `qro:` term codes (`device`, `line`, `value`, `Question`) are terms of RO-Crate's own context, so mapping the
  codes as bare keys in the Profile Crate's `@context` would redefine them; only the prefix `qro` is mapped.
- A Python script on Windows that reads a file and writes it back through `Path.write_text` writes CRLF, which `.gitattributes`
  (`* -text`) commits as it is. `tests/p4/test_p4_files.py` holds P4's files to LF.
